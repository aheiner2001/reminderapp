# TODO — Recommended build roadmap

Updated October 2, 2026. Completed implementation items are checked; unchecked items still need setup or future development.

The testing app now uses Next.js on Vercel, server APIs with Firebase Admin, and Resend test emails. Automatic scheduled delivery remains a later milestone. See [deployment setup](docs/DEPLOYMENT.md).

## Recommendation
Build a responsive web app first using TypeScript/React, Firebase Google Authentication, Firestore, Vercel hosting, a future scheduled backend, and Resend. Start with an invite-only free pilot. Add browser push later, then SMS if users want it. Android is a valid alternative if the priority becomes offline phone notifications.

See [full specification](docs/superpowers/specs/2026-10-02-birthday-reminder-design.md). The delivery rules in that document remain authoritative. This roadmap adds platform, access, costs, and future billing decisions.

## Android versus web
| Option | Can notify the phone? | Benefits | Limits |
|---|---|---|---|
| Native Android | Yes: local scheduled notifications; optional FCM remote push | Local reminders can work offline without email/SMS fees or a sending server | Android only; notification permission, background timing, reboot/timezone rescheduling, and app distribution need work |
| Responsive web app | Yes: optional web push on supported browsers after permission | Easy link sharing, desktop and mobile, one application | Email/push scheduling needs a backend; web timers cannot reliably run when closed |
| Installable PWA | Supported devices can install it and receive web push | App-like experience with shared web code | Platform/browser support varies; not equivalent to native scheduled local alarms |

Android 13+ requires notification permission for ordinary notifications. Prefer inexact scheduling for birthdays rather than promising minute-exact delivery. Rebuild schedules after reboot, date/time changes, and event edits. Handle denied permissions visibly. FCM push and local notifications are different: FCM receives a server message; a local notification is generated by the installed app. Neither is an SMS.

Web push requires permission, HTTPS, a service worker, device tokens/subscriptions, server sending, and testing on target devices. Include unsubscribe, expired-token cleanup, and per-device settings. Do not make push the only reminder channel in the pilot.

Firebase Authentication and Firestore have no-cost allowances. Firebase Hosting can serve a static frontend; scheduled Functions require the Blaze billing plan. Scheduler jobs, compute, networking, builds, and domain ownership are separate potential costs. Billing alerts are not a hard spending cap. A tiny pilot may use mostly included allowances, but do not promise zero charges.

If billing activation is unacceptable, prototype event management and previews on Spark first; evaluate a separately hosted scheduler/backend before enabling automated sending. Do not imply Spark alone performs scheduled email. GitHub Actions cron is a possible low-stakes experiment but may be delayed and has plan/inactivity constraints; it is not the recommended reminder production scheduler.

## Delivery providers — options
Pricing snapshots checked October 2, 2026; verify again when creating accounts. Free-tier numbers are provider limits for the whole app, not per user.

| Channel/provider | Pilot allowance or cost model | Recommendation |
|---|---|---|
| Resend email | Free transactional plan: 3,000/month, 100/day | First choice for TypeScript integration |
| Brevo email | Free plan: 300 email sends/day; verify transactional availability and branding | Alternative if its API/workflow fits |
| Postmark email | Developer plan: 100/month | Useful for delivery testing; small for daily pilot traffic |
| Twilio SMS | Paid sender, message segments, carrier and onboarding costs | Candidate when SMS is justified |
| Telnyx SMS | Paid message parts plus applicable sender/carrier/onboarding charges | Compare total cost and integration effort |
| Firebase Cloud Messaging | Messaging service is no-cost; backend operation is separate | Optional device notifications rather than SMS |

Five testers receiving at most one scheduled email a day use up to 155 scheduled emails in a 31-day month, plus tests and verification traffic. They fit Resend's published caps with substantial headroom. An email containing several birthday entries is one send; sending separate emails for each entry increases usage. Daily SMS digests may span multiple billed segments.

No access to users' inboxes/text messages is needed. The app sends to the user's supplied destination from its own sender. Do not build production SMS around email-to-SMS gateways or consumer Gmail passwords.

## Phase 6 — Charge customers later
Recommended model: Google sign-in stays free; app features/reminder delivery require an active subscription, with an administrator-controlled free tester exception. Decide monthly versus annual pricing only after measuring costs and value. Do not collect payment details yourself.

1. User signs in with Google.
2. Backend checks an active paid entitlement OR a free tester entitlement.
3. Non-entitled user sees pricing and clicks Subscribe.
4. Backend creates a Stripe Checkout subscription session using an approved server-side price ID; associate Firebase UID with the Stripe customer.
5. Stripe handles card collection and payment.
6. A signature-verified webhook updates the server-owned subscription record.
7. The app and scheduler enforce the entitlement. A success-page redirect alone never grants access.
8. Stripe Customer Portal lets the user update payment details or cancel.

- [ ] Create Stripe test-mode products/prices and server-side Checkout endpoint.
- [ ] Bind customer/subscription IDs to Firebase UID; do not rely on matching email alone.
- [ ] Process checkout completion and subscription/invoice changes idempotently; reconcile current Stripe state if events arrive out of order.
- [ ] Enable access only for confirmed eligible subscription states; define trial and failed-payment policy.
- [ ] Proposed policy: paid access ends at the current period end after cancellation; on unresolved failed payment, pause new sends once the entitlement expires.
- [ ] Recheck entitlement immediately before sending; clients cannot set paid status.
- [ ] Add Customer Portal, purchase history, cancellation messaging, and a server-side admin tester exemption.
- [ ] Preserve read/export/delete access to the user's data when sending entitlement ends.
- [ ] Test successful payment, declined payment, renewal failure, cancellation, refund policy, duplicate webhook, and tester access.
- [ ] Measure hosting, email, SMS segments, Stripe fees, support, and taxes before choosing prices.
- [ ] Configure live-mode billing only when launch-ready.

Payment processors charge fees. Free provider allowances do not make an unlimited paid product sustainable. For a native Android paid release, separately review current Google Play billing/distribution policies; the Stripe web flow here is for the website and should not be copied blindly into an Android purchase flow.

## Definition of pilot ready
- [ ] Only invited verified users can access their own events.
- [ ] Each scheduled message follows the spec and appears correctly in delivery history.
- [ ] Unsubscribe, revoke-access, archive, and account deletion stop future sends.
- [ ] Concurrent jobs and transient failures are tested without intentional duplicate sends.
- [x] No real email allowlist, provider secret, or service-account key is committed.
- [ ] A tester can manage events and receive reminders without leaving the website open.
